# 协作规范

本项目采用简化的 Git Flow：`main` 常驻可发布，功能与修复都在短分支上完成，
通过 Pull Request 合并，合并后删除分支。

## 1. 分支命名

| 前缀 | 用途 | 示例 |
| --- | --- | --- |
| `feature/` | 新功能 | `feature/pow-difficulty` |
| `fix/` | 缺陷修复 | `fix/genesis-prev-hash` |
| `docs/` | 文档 | `docs/quickstart` |
| `refactor/` | 重构（不改行为） | `refactor/cli-parser` |
| `release/` | 发布准备 | `release/v1.0.0` |

## 2. 提交信息

采用 Conventional Commits：

```text
<type>(<scope>): <subject>

[optional body]
```

- `type`：`feat` / `fix` / `docs` / `test` / `refactor` / `chore`
- `subject`：中文或英文均可，不超过 50 字，动词开头

示例：

```text
feat(block): 支持可配置的挖矿难度
docs(readme): 补充快速开始与运行效果
fix(chain): 修正创世区块前哈希校验
```

## 3. 开发流程

```bash
git switch main
git pull --rebase
git switch -c feature/xxx
# ... 编码、测试 ...
python -m unittest discover -s tests -v
git add .
git commit -m "feat(xxx): ..."
git push -u origin feature/xxx
# 在 GitHub 上发起 Pull Request，至少 1 人 review 后 squash merge
```

## 4. 代码风格

- 遵循 PEP 8，行宽 100；
- 所有公开函数写中文 docstring；
- 新增逻辑必须配套单元测试；
- 不引入第三方运行时依赖（保持「零依赖」这一核心卖点）。

## 5. 冲突处理原则

1. 先 `git fetch`，在本地复现冲突；
2. 理解双方意图后再合并，不做「无脑保留一边」；
3. 解决后必须重新跑测试，并在提交信息中说明取舍理由；
4. 冲突解决提交使用 `merge:` 前缀，便于回溯。
