# 设计说明

本文说明 MiniChain 的设计目标、数据结构、核心算法与已知局限，供二次开发与课堂讲解使用。

## 1. 设计目标

| 目标 | 具体做法 |
| --- | --- |
| 可解释 | 每一步都打印中间结果（nonce、耗时、哈希前缀） |
| 可运行 | 只用标准库，`python -m minichain demo` 一条命令跑通 |
| 可修改 | 分层清晰：`block.py` 管数据、`chain.py` 管规则、`cli.py` 管交互 |
| 可测试 | 核心逻辑与 IO 解耦，10 个单元测试 0.1 秒内跑完 |

## 2. 数据结构

```text
Block
├── index          区块高度（创世块为 0）
├── timestamp      出块时间戳（秒）
├── transactions   交易列表（字符串）
├── previous_hash  前驱区块哈希（64 位十六进制）
├── nonce          工作量证明计数器
├── difficulty     目标难度
└── hash           本区块 SHA-256
```

参与哈希计算的字段通过 `Block.payload()` 序列化为**排序、紧凑**的 JSON，
保证跨平台、跨 Python 版本得到相同字节序列：

```python
json.dumps(data, ensure_ascii=False, sort_keys=True, separators=(",", ":"))
```

## 3. 核心算法

### 3.1 工作量证明

```python
target = "0" * difficulty
while True:
    block.hash = sha256(block.payload())
    if block.hash.startswith(target):
        break
    block.nonce += 1
```

难度每 +1，期望尝试次数 ×16；因此难度 4 在普通笔记本上约 0.1～1 秒出块，
既能看到「等待」，又不至于让学生等太久。

### 3.2 整链校验

校验分三层，任一失败立即返回原因：

1. 创世区块的 `previous_hash` 必须是 64 个 `0`；
2. 每个区块的哈希必须能被复算，且满足难度；
3. 相邻区块必须首尾相接，高度连续。

### 3.3 篡改检测

攻击者修改第 k 个区块的交易后，该区块的 `compute_hash()` 结果与保存的 `hash` 不再相等，
校验在第 k 个区块处即失败；即便攻击者重算第 k 个区块的哈希，
第 k+1 个区块的 `previous_hash` 又会失配——除非重算后续所有区块并重新挖矿，
这正是「篡改成本随链长指数上升」的直观体现。

### 3.4 最长链共识

`replace_with()` 只在同时满足「更长」与「合法」时替换本地链，
对应比特币「最长链即主链」的简化规则。

## 4. 复杂度

| 操作 | 时间复杂度 | 说明 |
| --- | --- | --- |
| 出块 | O(16^d) | d 为难度，期望尝试次数 |
| 校验 | O(n) | n 为区块数 |
| 导出 JSON | O(n) | 全量序列化 |

## 5. 已知局限

- 交易没有签名，任何人可伪造交易内容；
- 没有 P2P 网络与内存池，单机演示；
- 没有默克尔树，交易列表直接进区块；
- 不做持久化事务，`save()` 为整体覆盖写。

以上局限均在 [路线图](../README.md#路线图) 中列出，欢迎通过 Issue 讨论。

## 6. 目录职责

```text
minichain/block.py   数据结构 + 哈希 + PoW（无 IO）
minichain/chain.py   链规则 + 校验 + 共识（无 IO）
minichain/cli.py     参数解析 + 终端输出（唯一的 IO 层）
tests/               仅依赖公开 API，不 mock 内部实现
```
